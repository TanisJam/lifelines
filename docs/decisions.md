## 001 — The event log is the source of truth

- **Decision:** the simulation appends typed events: `{ year, kind, actors, payload, causes }`. Biographies are rendered from those events with templates. No generated text is ever authoritative.
- **Why:** this is how Dwarf Fortress works: it simulates first and describes afterwards (see [research](./research.md#dwarf-fortress)). It keeps the story consistent with the state and makes "why did this happen?" answerable through `causes`.

## 002 — Keyed RNG instead of a sequential stream

- **Decision:** every random draw comes from `hash(worldSeed, personId, year, decisionKind)`.
- **Why:** with one sequential stream, a single edit shifts every later draw, so unrelated lives change for no in-world reason. That is noise, not a butterfly effect. With keyed draws, an edit propagates only through **state**. A decision flips only when its probabilities move across a draw that stayed fixed. The result is a butterfly effect that is causal and explainable.
- **Prior art:** this technique is known as *Common Random Numbers*, and the RNGs built this way are called counter-based (Philox, Random123). See [research](./research.md#counterfactual-simulation).

## 003 — Jev decides, code handles biology

- **Decision:** social and psychological choices (romance, marriage, moving, career, having a child, feuds) are Jev judgments. Aging, fertility windows and mortality are computed in code.
- **Why:** Jev returns calibrated probability distributions over options, not text, so the engine can sample them directly. That replaces a hand-tuned table of rules. Biology is cheaper and more accurate as plain math.

## 004 — Pin the model and cache every judgment

- **Decision:** use `jev-1.13.0`, not the `jev-latest` alias. Cache every judgment, keyed by `(questionId, relevant state)`, on disk under `.cache/`.
- **Why:** the [determinism experiment](./findings.md#determinism-experiment) showed that identical calls vary by up to 0.11 in probability. Without the cache, re-simulating a fork would inject sampling noise that looks like fake butterflies. The key must contain only the state that matters to that decision; otherwise any edit invalidates unrelated answers.

## 005 — Hexagonal engine with a `DecisionMaker` port

- **Decision:** `src/domain` is pure TypeScript and imports neither Next nor the SDK. The port has two adapters: `RuleDecisionMaker` (deterministic, for tests and offline dev) and `JevDecisionMaker`.
- **Why:** it keeps the tests fast and free, and makes the engine swappable.

## 006 — Server state lives on `globalThis`

- **Decision:** the world store and the decision engine singletons are attached to `globalThis`.
- **Why:** Next bundles Route Handlers and Server Components separately. Module-level singletons silently become two copies: API routes worked while the pages returned 404.

## 007 — Every link is a recorded decision

- **Decision:** persist a `Decision { personId, year, question, options[{id, p}], noise, chosen, source, causes }` for every choice point, including the ones that resolved to "nothing happens".
- **Why:** the UI needs to show, at each link, the options that existed, how Jev weighed them, where the draw fell and what was chosen. Events alone hide all of that.
- **Implemented as:** `DecisionRecord` in `src/domain/decisions.ts`, with `jevRaw`/`prior`/`final` split (see 016), `noise` per option id, `margin` (see 009), `source: "jev" | "rules" | "biology" | "forced"`, `causes` (event ids), and `resultingEventIds`. "Including the ones that resolved to nothing happening" is bounded by a recording threshold (`RECORD_THRESHOLD = 0.05` in `simulate.ts`): a biology decision (illness, death, immigration) is only kept if it actually fired OR the road not taken had ≥5% probability — otherwise a "did nothing happen" record for every person, every year, would dwarf the interesting decisions. Social decisions (the seven `DecisionKind`s) are always recorded once asked, since the code-level gates that precede them (e.g. "did this person even attempt to seek a partner this year") already filter out near-certain "no" years — those gates themselves are NOT recorded as decisions, only what they gate.
- **Deviation:** decisions don't carry a `p` per option inline on `options[]`; probabilities live in `final`/`jevRaw`/`prior` keyed by option id instead, so a decision's odds can be shown at three different stages without duplicating the option list three times.

## 008 — One generic override

- **Decision:** the only edit operation is "at decision D, choose option X", which replaces the six hand-coded kinds (force or prevent a marriage, force or prevent a move, change job, prevent death).
- **Why:** every link becomes editable without writing per-kind code. Validation shrinks to a single rule: the option must exist at D.
- **Implemented as:** `Override { id, decisionId, optionId }` in `src/domain/types.ts`. `decisionId` is content-derived and self-describes its year (`<kind>:<personId-or-pairKey-or-"world">:<year>`, see `decisionYear()` in `decisions.ts`), so a fork needs no separate `year` field. `validate-override.ts` re-derives the exact candidate set for that year via `gatherCandidatesForYear` (the same pure function `simulate()` itself uses to gather candidates) rather than hand-rolling eligibility rules per kind — so validation and simulation can never disagree about what decisions exist. "Prevent a death" is exactly choosing `"survive"` at that person's `death:<personId>:<year>` decision, as anticipated; the other five old kinds map the same way (e.g. `change-job` is choosing a job option at a `career-change` decision). The old typed `Override` variants and their UI (`EditPanel`) were removed, not kept internally.

## 009 — Gumbel-max sampling

- **Decision:** choose `argmax_i(log p_i + g_i)`, where `g_i` is keyed Gumbel noise per option: `hash(seed, person, year, decision, optionId)`.
- **Why:** inverse-CDF sampling with a single uniform depends on the order of the options, and shifting an unrelated option can flip the outcome. Gumbel-max guarantees *counterfactual stability*: raising the probability of the outcome that happened never flips it (Oberst & Sontag 2019). Butterflies then reflect real causes.
- **Implemented as:** `sampleGumbelMax` in `src/domain/rng.ts`, replacing `sampleDistribution` (removed). **Margin** (decision 009 asked for one definition, documented and tested): `margin = final[chosen] - final[runner-up]`, clamped to ≥ 0, computed from the *probabilities* (not the Gumbel scores) — see `decisionMargin`. A margin near 0 means either a near-50/50 toss-up, or the noise picked a real underdog (e.g. a 1%-vs-99% split where the 1% "won"); both read as "close call" in the UI, which is intentional (both are moments where the story could plausibly have gone the other way) but can look surprising next to a "1%" label — noted as a known nuance, not fixed this round. Tests in `rng.test.ts` cover determinism, that different keys can choose differently for an identical distribution, and counterfactual stability (raising the chosen option's probability, holding the noise key fixed, never flips the outcome) swept across 100 keys.
- **Also fixed by this change:** `ruleDistribution`'s `career-change` branch returned raw relative weights, not a normalized distribution — harmless for Gumbel-max sampling itself (invariant to a constant scale factor on every option) but broke `decisionMargin`, which needs an actual `[0,1]`-summing distribution. Fixed at the source (`rule-heuristics.ts`) plus a defensive `normalizeDistribution` helper.

## 010 — Stream the simulation over SSE

- **Decision:** the simulate and fork endpoints stream year ticks as `text/event-stream` from a Route Handler.
- **Why:** a Jev world takes about 15s (up to ~30s with the fuller decision set). Streaming turns that wait into the "watch lives being built" experience.
- **Implemented as:** `POST /api/worlds/stream` and `POST /api/worlds/[worldId]/edit/stream`, backed by `sseResponse()` (`src/server/sse.ts`, a `ReadableStream`-based helper) and `simulate()`'s existing `onYearComplete` callback. Frames: `start`, one `tick` per simulated year (that year's new events + new `DecisionRecord`s + running living population), and a final `done` with the created/forked branch id and stats — `done` carries everything a caller who ignores every `tick` would need, so there's a natural non-streaming-equivalent fallback (and the original non-streaming `POST /api/worlds` and `POST /api/worlds/[worldId]/edit` routes are kept, unchanged in contract, for programmatic/test use). Browsers' `EventSource` is GET-only, so the client reads the POST response body manually (`src/lib/sse.ts#streamSSE`) instead.

## 011 — "The Loom" is the main UI

- **Decision:** the main view shows one storyline lane per person, with time on the x-axis. Marriages join lanes, births start them and deaths end them. Forks render like a git graph, with the old branch kept as a dashed ghost. Clicking a link opens an inspector showing each option's probability as a bar, a needle where the draw fell, and a tag on close calls. The stack is custom SVG plus Motion.
- **Why:** it is the only concept researched that shows both the weave of many lives and click-to-fork with ghosts. Alternatives are in [research](./research.md#ui-concepts).
- **Implemented as:** `src/components/loom.tsx`, hosted at `/world/[worldId]` (replacing the old person-card grid). Lane order is a simple family-grouped heuristic (`buildLoomPeople` in `domain/loom-data.ts`: DFS from founders, spouse immediately after spouse, children right after their mother sorted by age) — not full StoryFlow crossing minimization, per the brief. Marriages draw a short connector between spouse lanes at the marriage year; births draw a connector from the mother's lane to the child's; deaths end a lane with a `†`; immigrants' lanes start at their arrival year with a small marker; a moved-away person's lane continues dashed. Decision dots are sized by `1 - margin` and colored by kind (brass for social/life events, crimson for illness/death), with a crimson ring for a close call (`margin < 0.15`). Clicking one opens the inspector: question, each option as a bar (`final`), small tick marks for `jevRaw` and `prior` where present, the chosen option checked, a close-call tag, and a "Choose this instead" button per non-chosen option that triggers a streamed fork (decision 010) with a live progress overlay. After a fork, the page navigates to `?branch=<new>&compare=<base>`; the Loom then renders the base branch's lanes as a dashed ghost underneath the new branch's solid ones, highlights diverged lanes in brass, and shows a one-line diff summary (changed / newly-born / never-born counts) above the timeline, reusing `diffBranches`. The per-person biography page is kept, linked from each lane's label.
- **Deviations from the brief, disclosed:** the inspector's "needle where the draw landed" is represented as the highlighted (checked) bar rather than a literal needle on a shared number line — Gumbel-max doesn't produce a single-axis cumulative position the way inverse-CDF sampling did, so there's no one natural spot to put a needle. "Why?" in the inspector is a short pointer to the full causal chain on the person's biography page (reusing the existing `CauseChainButton`/`/causes` machinery) rather than an inline expandable tree, to keep the inspector panel compact. Responsiveness is horizontal-scroll-only (sticky name column, `overflow-x-auto` timeline), per the brief's "horizontal scroll ... is fine."

## 016 — Jev decides alone; the code-side blend is removed

- **Decision:** when the engine is Jev, a social decision's `final` distribution IS `jevRaw` — unweighted by any code-side prior. The 0.65/0.35 blend introduced in decision 013 is removed entirely, not just moved. `RuleDecisionMaker` remains only as the offline/test adapter (and the source of `prior` for decisions where Jev genuinely wasn't asked — the rules engine, and biology). This **supersedes 013 in full**, including the storage-layer correction 016 originally meant to be (keeping `jevRaw`/`final` separate survives; the "blend as an explicit policy step" part does not — there is no blend step at all now).
- **Why:** the product wants Jev to decide coherently by impersonating each person — their life, emotions and state — not have its judgment second-guessed by a hand-tuned heuristic. Coherence with a person's inner life is the goal here, not base-rate calibration against a rule table. A code-side weight is exactly the kind of silent thumb-on-the-scale that works against that: it launders Jev's actual judgment before anyone (the UI, a log, a future analysis) ever sees it.
- **Where the demographic safety net comes from instead:** not from weights, but from **decision 012** (worldgen) — pre-seeded founder families with existing children, and occasional immigration — which guarantees a multi-generational, causally-connected town regardless of how any given `DecisionMaker` answers romance/marriage/child questions. That was already the primary fix for the original "town dies out" failure; the blend was a secondary, smaller correction on top of it, and removing it doesn't remove the primary fix.
- **If Jev alone makes marriages or births rare again:** do not re-add weights. The intended fix is round 4's richer inner-life state for Jev (DF-style personality facets, values, needs, emotions, memories, relationships with opinion scores) — giving Jev more of the person to actually decide from, rather than correcting its answer after the fact. `personSummary()` in `simulate.ts` already has a documented extension point for this: the richer state slots into the same named `self`/`partner`/`other` objects with no restructuring of `DecisionQuestion`, `DecisionRecord`, or any caller. See `docs/findings.md` for whether this round's live run actually showed the regression or not.

## 012 — Family-seeded demographics

- **Decision:** `generateWorld` no longer produces a flat pool of unrelated adults aged 16-55. It seeds several founder couples (already married, with 0-3 existing children aged 0-15), a pool of unattached young singles, and a few elders. `simulate` also rolls occasional newcomers (immigration) once the living population runs low, and forces romance candidates to prefer age-appropriate partners (within 10 years, widening only if nobody nearby qualifies).
- **Why:** the [first live run](./findings.md#2026-09-21--first-live-jev-run-seed-butterfly-1) showed *zero births in 75 years*: with every founder an unattached adult and no age-appropriate matching, marriages (when Jev accepted them at all) happened as late as the mid-50s — well past the fertile window — so no second generation was ever born. Pre-seeding families guarantees a multi-generational town regardless of how conservative a given `DecisionMaker` turns out to be about romance, and immigration keeps the partner pool from running dry in a small town over 75 years.
- **Verified:** [second live Jev run](./findings.md#2026-09-21--second-live-jev-run-post-fixes-seed-butterfly-2), plus a rules-engine sweep across 10 seeds (`scripts/check-demographics.ts`).

## 013 — Blend Jev with a code-side prior

- **Decision:** `JevDecisionMaker.decide()` blends Jev's returned distribution with `RuleDecisionMaker`'s (same question, same state) at a configurable weight (`blendWeight`, default 0.65 Jev / 0.35 rule; env `JEV_BLEND_WEIGHT`). The blended distribution is what gets cached and sampled.
- **Why:** per the iteration brief, question wording and state came first — `DECISION_INSTRUCTIONS` for `accept-partner`, `marry`, `have-child` and `reconcile` now state the ordinary village base rate explicitly ("most couples who've been courting a while do go on to marry..."), since the bare wording measured as systematically conservative. The blend is the second, smaller correction: it also damps the model's own sampling noise (up to 0.11 spread on identical state — see the [determinism experiment](./findings.md#2026-09-21--determinism-experiment)), which matters independently of any bias, since that noise would otherwise read as a fake butterfly on re-simulation.
- **Trade-off:** at `blendWeight: 0.65`, Jev is still the majority signal, but a pure "what does Jev alone think" reading of any single decision is no longer directly recoverable from the cached distribution. Worth revisiting if the wording fix alone turns out to be sufficient once measured over more seeds.

## 014 — Content-derived ids for children and immigrants

- **Decision:** a child's id is `child-<motherId>-<year>`; an immigrant's is `immigrant-<year>`. Neither uses the incrementing counter (`p004`, `p005`, ...) the original founders use.
- **Why:** the counter was positional — the Nth person ever created got id `p0XX` regardless of who they were. Across a fork, once earlier decisions diverge, "the Nth person created" can be a completely different individual in the base branch vs. the fork. `diffBranches` compares people by id, so this showed up as a real bug during the second live run: a fork that prevented a marriage (so its child was never conceived) reused that child's numeric slot for an unrelated later birth, and the diff reported it as "Ivo Hallowmere's job and spouse changed" instead of "Ivo was never born; Kira was born instead." A mother has at most one child per year and at most one immigrant arrives per year (both by construction of their respective gates), so `motherId+year` and `year` alone are already unique keys — no counter needed, and the id is now stable and comparable across any two branches that share history up to that point.
- **Verified:** edit 2 in the [second live Jev run](./findings.md#2026-09-21--second-live-jev-run-post-fixes-seed-butterfly-2) shows a real `immigrant-1546` correctly appearing in `newPeople`.

## 015 — Validate before forking

- **Decision:** `validateOverride` (in `src/domain/validate-override.ts`) checks an override against the exact snapshot `forkWorld` would restore and build from (year `override.year - 1`) *before* the edit route calls `forkWorld`. It rejects: a year outside the world's span, a person who doesn't exist, isn't yet born, or is already dead at that year, a marriage target who isn't yet an adult, a forced marriage where either side is already married to someone else, and a prevented marriage that's already happened.
- **Why:** the first live run's edit route returned `200` with an empty diff for `force-marriage` on someone already dead — silently doing nothing instead of failing loudly. `applyForcedOverridesForYear` already guarded against a missing/dead person internally (so it never corrupted state), but that guard is invisible to the caller: a no-op fork looks identical to a real edit that genuinely changed nothing. Validating up front, against the same restored state the fork will actually use, turns that into an actionable `400` with a specific reason.
- **Also:** the client (`EditPanel`) mirrors these same checks to filter which partners/years it offers in the first place, so the common case never needs a round trip to discover it's invalid — but the server-side check is the actual authority.

## 017 — PersonMind and a prioritized situation catalog subset

- **Decision:** every person now carries a `PersonMind` (`src/domain/mind.ts`): 12 facets (0-100), 7 values (-50..50), a dream (goal + status), needs, up to 8 decaying thoughts, up to 5 memories (with a 1-in-3 chance of becoming "core" and shifting a facet), and a top-5 relationship list with a strength/bond. `createMind` blends a child's facets/values from both parents (plus noise) when parents are known, or a per-family value bias for founders, so families read as families rather than 55 independent random people. Every social `DecisionQuestion` sent to Jev now includes `self.mind` (compact JSON) and `self.portrait` (a rendered prose sentence built from the mind's most extreme facets/values, `renderPortrait`) — Jev is asked to *impersonate* the person described, not judge a population-level base rate. Code still decides *which* situation a person faces and *when* (a trigger + keyed RNG gate in `gatherCandidatesForYear`); Jev decides *how they respond*, using nothing but who they are. After an outcome, code deterministically updates the mind (`pushThought`/`addMemory`/`applyCoreMemoryShift`/`updateRelationship`) so the next decision this person faces reflects what just happened to them.
- **Why:** `docs/mind-model.md`, itself grounded in Dwarf Fortress's thought/memory/relationship system (`docs/research.md#dwarf-fortress-inner-life`) — the product goal is rich, causally-coherent DF-style biographies, and decision 016 already committed to Jev deciding alone with no code-side weight. A bare "does this person accept?" question with no inner life to draw on has nothing to be coherent *with* across a person's life; this is the round-4 answer to "if Jev alone makes marriages/births rare again, the fix is a richer mind, not weights" (016's own closing note).
- **Scope, disclosed:** `docs/mind-model.md` specifies a full catalog of situations (C1-C4 childhood, Y1-Y5 youth, A1-A11 adulthood, O1-O4 old age — roughly two dozen). Given this round's time budget, only a prioritized subset spanning courtship through career, conflict, dreams and breakdowns is implemented: **Y1** (someone shows romantic interest), **A1** (propose or end a courtship), **A2** (try for a child), **A3** (a specific job opportunity), **Y3** (leave for a distant opportunity or stay), **Y4** (a first grudge), **A6** (an old feud, reconcile/continue/sabotage), **A8** (a dream check, every 5 years while unrealized), **A11** (a breakdown once stress crosses a threshold, kind picked by code from the dominant facet — rage/despair/withdrawal — then Jev decides how the person copes). Not implemented this round: C1-C4, Y2, Y5, A4, A5, A7, A9, A10, O1-O4 — these fall back to the pre-round-4 code paths (aging/biology) or simply don't occur; see the "Status" note at the top of `docs/mind-model.md`.
- **Verified:** `src/domain/mind.test.ts` (determinism, parent-blend inheritance, thought decay/stacking, core-memory promotion and its facet shift, memory/relationship caps, relationship drift) and `src/domain/situations.test.ts` (each new trigger fires/doesn't fire under the right conditions, decision ids are stable). A live Jev world (seed `mind-1`, see [findings](./findings.md)) shows population staying healthy across 75 years with **zero code-side weight** — directly testing 016's prediction.
- **Known limitation, disclosed, not fixed this round:** A8's "dream realized: leave for the city" outcome is not cross-checked against whether the person actually has a `move` (Y3 "leave") event on record — a person can narrate "this dream was realized" while never having left town. Fixing it needs A8's resolution to look up the person's own event log before declaring the goal realized; left as a follow-up rather than done under time pressure.

## 018 — `fragility` and `surprise` replace `margin`

- **Decision:** `DecisionRecord.margin` (decision 009) is removed and replaced with two independent fields: `fragility` (the gap between the winning and runner-up **Gumbel scores**, `log p + g`, not probabilities — small means a small nudge would have flipped the outcome; `NOT_FRAGILE = 999`, a finite JSON-safe sentinel, for a forced or single-option decision) and `surprise` (a boolean: the chosen option's own probability was below a threshold, default 20% — a long shot that won). `src/domain/rng.ts#decisionFragility` / `#isSurprise`. The Loom inspector (`src/components/loom.tsx`) shows these as two separate badges — "Close call" (crimson, fragility) and "Long shot" (brass, surprise) — instead of one "Close call" tag.
- **Why:** decision 009's own text already flagged the flaw: a probability-gap `margin` conflates "this was genuinely a toss-up" with "a heavy favorite happened to lose to noise" — both read as "close call" even though only the first one actually *was* fragile to a small change. The two are different questions a reader of a biography would ask ("could this plausibly have gone the other way?" vs. "was this an upset?"), so they need separate signals, not one overloaded one. This is a direct fix for round-3 screenshot issue B1.
- **Verified, live:** a real A8 decision where the chosen option (`abandon-it`, 14% probability) was correctly flagged `surprise: true` with only moderate `fragility` (1.83), alongside a separate, decisive 97%-favorite win correctly flagged not fragile (`fragility: 8.53`) — confirming the two signals actually diverge on real data, not just in theory. `src/domain/rng.test.ts` covers determinism, the `NOT_FRAGILE` sentinel, and a worked example where a long-shot win is not necessarily fragile.

## 019 — Given names unique among the living

- **Decision:** `pickUniqueName` (`src/domain/names.ts`) scans the name pool starting from the deterministically-picked index and returns the first candidate not already held by anyone currently alive in the world; if the whole pool for that sex is exhausted (small towns won't hit this), it falls back to an epithet ("... the Younger"). `worldgen.ts` and `simulate.ts`'s child/immigrant spawners now pass the live `existingNames` set through, replacing the old plain `pickName`.
- **Why:** round-3 screenshots showed two simultaneously-living "Silas Hallowmere"s in the same town — confusing in the Loom (two lanes with the same label) and in prose ("Silas Hallowmere and Silas Hallowmere..."). Fix is scoped to *the living*, not globally-ever-used: two people separated by decades sharing a name (a namesake, or an old name recycling after the first died) is realistic and doesn't cause the ambiguity that a same-generation collision does.
- **Verified:** a throwaway uniqueness check (not kept in the repo) across 3 worldgen seeds (46, 35, 47 people) found 0 duplicate names among the living in any of them.

## 020 — The Loom shows weaving: marriage bands, birth curves, relationship arcs

- **Decision:** three changes to `src/components/loom.tsx` and `src/domain/loom-data.ts`, addressing round-3 screenshot issue B3 ("lanes read as flat parallel lines"): (1) `buildLoomPeople`'s lane-ordering pass now re-splices a newly-married spouse to sit immediately adjacent to their partner's lane whenever the DFS-derived order didn't already put them there, so a marriage draws a short, visible connector instead of an arbitrary long one; (2) a marriage renders as a translucent filled band spanning from the marriage year onward between the two lanes (plus a solid connecting line when adjacent), and a birth renders as a bezier curve from the mother's lane to the child's, rather than a straight tick; (3) hovering a lane draws quadratic-bezier arcs to that person's top relationships — brass for friend/lover bonds, dashed crimson for grudge/rival — sourced from `LoomPerson.relationships` (now populated from `person.mind.relationships`).
- **Why:** the round-3 screenshot review called the Loom "readable but visually flat" — the underlying family/relationship structure that the simulation actually tracks wasn't visible in the chart at all, just parallel same-length lines with dots.
- **Also, same fix (B2 — dot-count clutter):** the Loom hides non-noteworthy decision dots (a routine yearly roll that produced no event, wasn't forced, wasn't fragile, and wasn't a surprise) by default, with a "show all rolls" checkbox in the legend to reveal every roll. Dot count dropped from showing every roll to 393/916 visible by default in the seed-`mind-1` run.
- **Honest critique of the result (screenshots in the scratchpad, `r4-loom.png`/`r4-inspector.png`):** the marriage bands and birth curves are a real, visible improvement over round 3's flat lines — a family cluster is now recognizable at a glance. Lane ordering is still the same DFS-plus-splice heuristic, not true crossing-minimization (StoryFlow-style), so a town with many cross-family marriages will still show some long, crossing connector lines; and relationship arcs are hover-only, so the "weave" for grudges/friendships isn't visible without interacting — a static "always show top-1 relationship arc per lane" mode was considered but not built, to avoid reintroducing B2's clutter.

## 021 — Escalated feuds get their own prose

- **Decision:** `narrateEvent`'s `"feud"` case now checks `event.payload.escalated` (set by the A6 "sabotage" outcome) and renders "struck back at" / "escalated the feud further" instead of "began a bitter feud" for a feud event that continues an already-ongoing one.

## 022 — Feud cooldowns and the dead-actor guard

- **Decision:** two related fixes, both under "a chronicle needs a fresh trigger, not a monotone loop" (round 5 brief, point 1 and point 3). (a) **A dead person can never be offered as a decision's partner.** `A1` (proposal) and `A6` (feud continues/reconcile/sabotage) now re-check `isAlive(partner, year)` at candidate-gathering time, not just once when the romance/feud began — `activeRomancePair`/`activeFeudPair` only read the event log and don't know or care whether either party is still alive. (b) **A feud needs a fresh trigger.** `feudPairHistory(events, personId)` permanently excludes anyone this person has EVER had a `feud` or `reconciliation` event with from being picked as a NEW `Y4` rival again, capped further by `MAX_FEUD_PAIRS_PER_LIFE = 3` distinct rivals per life. Within one still-unresolved feud episode, `FEUD_EPISODE_CAP = 3` and `FEUD_EPISODE_WINDOW_YEARS = 12` bound how many times `A6` re-asks before code just leaves it be. A durable reconciliation also now writes a memory (`addMemory`), not just a thought, so it can resurface later as "…remembering the peace they made."
- **Why:** the round-4 sample biographies (Orla Cinderfell, Kira Juniperwick) were feud → peace → feud → peace with the SAME one or two people, 5-6 times over, and a screenshot caught a reconciliation event dated a year AFTER one of the two parties had already died ("1564 — Fira Underhill and Orla Cinderfell made peace at last", Orla died 1563) — `A6`'s trigger checked the feud was still "active" in the event log but never checked either party was still alive.
- **Implemented as:** `src/domain/simulate.ts` — `feudPairHistory`, the `MAX_FEUD_PAIRS_PER_LIFE`/`FEUD_EPISODE_CAP`/`FEUD_EPISODE_WINDOW_YEARS` constants, and the `isAlive(...)` guards added to the `A1` and `A6` trigger blocks in `gatherCandidatesForYear`.
- **Verified:** `src/domain/situations.test.ts` — a dead feud/romance partner is never referenced by any candidate at any later year; a resolved feud pair is never re-offered as a NEW `Y4` grudge even though the trigger's facet condition still qualifies and the random gate still fires across a 66-year sweep; an already-3-times-escalated feud stops being offered to `A6` even at an otherwise "on schedule" year. Live-verified on a fresh seed (`chronicle-2`): Briala Oakhaven's feud with Loran Kestrelholt escalates twice (1500 → 1506 → 1509) and then never resurfaces for the rest of her 72-year life, instead of repeating every few years — see [findings.md](./findings.md).

## 023 — Gerund-form prose, and real dream realization

- **Decision:** two grammar/logic fixes. (a) Every `pushThought` "cause" string in `simulate.ts` (about 25 call sites) is now a gerund/noun phrase ("clashing with Petra", "making peace with Briala") instead of a past-tense sentence fragment ("clashed with Petra", "made peace with Briala") — the latter reads as broken grammar in `narrateThought`'s "felt X upon Y" template ("felt relieved upon made peace with Briala"). `DREAM_GERUNDS` (`src/domain/mind.ts`) maps each raw `DreamGoal` string ("leave for the city") to its gerund form ("leaving for the city") for every place a dream goal appears in prose; the raw form is kept as the programmatic value (matched against real events, see below) so nothing generated ever has to parse prose back out. (b) `dreamGoalSatisfiedBy(goal, events, personId)` gates `A8`'s "push-harder" outcome: even a favorable ambition/perseverance roll can no longer flip a dream to "realized" unless the matching REAL event already exists on that person's own log (an actual move-away for "leave for the city", an actual birth for "start a family", a real non-forced job change for "master a craft", a marriage or birth for "found something lasting").
- **Why:** both are round-5 screenshot-review findings: "dreamed of leave for the city" and "felt relieved upon made peace with Briala…" (broken grammar — a raw past-tense verb glued onto "upon"); and Orla Cinderfell's "leave for the city" dream being marked realized in 1506 despite her chronicle showing she never left town — a die roll alone shouldn't make a dream come true without the underlying life event.
- **Implemented as:** `src/domain/mind.ts` (`DREAM_GERUNDS`/`dreamGerund`), `src/domain/simulate.ts` (`dreamGoalSatisfiedBy`, and the gerund rewrite across every `pushThought`/`addMemory` cause string), `src/domain/narrate.ts` (the `dream` and `town` narration cases use `dreamGerund`).
- **Verified:** `src/domain/narrate.test.ts` — `narrateThought` never produces a broken `"upon <past-tense-verb>"` form across a representative set of real cause strings from the simulator; dream narration always contains the gerund form for all four `DreamGoal`s across `realized`/`abandoned`/`adjusted` outcomes; `src/domain/situations.test.ts` — `dreamGoalSatisfiedBy` is exercised directly for all four goals (a matching event returns `true`, an unrelated person or a merely-similar event — e.g. arriving vs. leaving, a forced job change — returns `false`).

## 024 — Traits derived from the mind

- **Decision:** the person page's "Traits:" line now calls `traitWords(mind)` (`src/domain/mind.ts`) instead of joining `person.traits` (a leftover round-1 field: 3 independently-random picks from a flat 16-word pool, unrelated to `PersonMind`). `traitWords` shares its ranking (`extremeTraits`) with `renderPortrait` — both pick the person's most extreme facets/values outside the neutral band, just render them as short adjectives vs. full sentences. - **Implemented as:** `SHORT_FACET_WORDS`/`SHORT_VALUE_WORDS` tables plus `extremeTraits`/`traitWords` in `src/domain/mind.ts`; `person.traits`/`TRAIT_POOL`/`pickTraits` are left in place (still used internally, e.g. worldgen bookkeeping) but no longer rendered anywhere.
- **Verified:** `src/domain/mind.test.ts` — across 100 different seeded minds, `traitWords` never contains both halves of any of the 19 known opposite word pairs; an artificially-neutral mind (every facet at 50, every value at 0) returns an empty trait list, matching `renderPortrait`'s own "even-tempered and unremarkable" fallback for the same mind.

## 028 — Depth fixes: worldgen's family-value bias, A8/A3 trigger design, inner-life prose

- **Decision, population decline (the real root cause, not seed variance):** traced with a live seed (`chronicle-3`) to `familyValueBias` in `worldgen.ts` — a founding couple shares one `familyIndex`, and when the random 1-2 strongly-biased values happened to include `family`, BOTH founders (and their whole line, via parent-blending) could land near the value's hard floor (-50) by pure chance. This would stay with her for years." for core memories. **Two grammar bugs found live while screenshotting this fix and fixed in the same pass:** both this new clause and the existing round-5 "the loss stayed with ___" death clause used the SUBJECT pronoun ("she"/"he") in an OBJECT position ("with she" / "with he" instead of "with her" / "with him") — added a proper `objectPronoun` helper and fixed both call sites. **Not done this round:** standalone "quiet" chronicle entries surfacing a core memory with no live event that year — deferred, disclosed.

## 034 — The single-life pivot

Round 9. The product shifts from "generate a town, browse it" to: the player names a newborn (a daughter, a son, or "let fate decide"), one protagonist — id always `"protagonist"` — is born in a medieval village, and the simulation writes their life until death. The player can then change any turn in the chronicle, including a turn decided by someone else or by chance, and the life is rewritten from that point. The whole village is still simulated underneath (Jev, or the rules engine, still plays every NPC), but the protagonist gets priority.

- **Split into a parallel `engine`/`ui` worktree pair**, with `src/contracts/life.ts` and `docs/design/single-life-contract.md` as the frozen contract between them (round 9's first commit, already in place before this entry). This entry documents the ENGINE side's implementation of that contract.
- **The protagonist's birth is real but not decision-backed.** `worldgen.ts`'s `GenerateWorldOptions.protagonist` (already scaffolded pre-round) injects the child into the FIRST founder couple at exactly `startYear`, age 0 — a real `birth` event, but with no `A2` candidate and no `DecisionRecord` behind it, so it structurally can never be forked. This is what "their birth is immutable" means in the engine, reinforced by an explicit guard in `validate-override.ts` (see decision 037) for the general case of a rewrite targeting any year before it.
- **A new, parallel store (`src/server/life-store.ts`), not a reuse of `world-store.ts`.** A "life" isn't a `Branch`/`WorldRecord`: different id space (`lifeId`/`branchId` vs `worldId`/`branchId`), and a different default-branch rule — `GET /api/lives/:lifeId` with no `branchId` returns the LATEST branch, not the original one, per the contract (§ "defaults to the latest branch"), which is the opposite of `world-store.ts`'s `originalBranchId` default. Follows decision 006's exact `globalThis`-attachment pattern for the same reason.
- **The old `/api/worlds/*` endpoints are untouched and still compile** — every change described in 035-039 is either a NEW file, or gated behind an optional `protagonistId` parameter that defaults to `undefined` and is a complete no-op when absent (verified: `simulate()` without `protagonistId` produces byte-identical output to before this round — see decision 037's test). The single-life product is additive, not a rewrite of the town engine.
- **Endpoints exactly per the contract:** `POST /api/lives/stream`, `POST /api/lives/:lifeId/rewrite/stream`, `GET /api/lives`, `GET /api/lives/:lifeId?branchId=`, `GET /api/lives/:lifeId/people/:personId?branchId=`. See decision 039 for the streaming design and decision 038 for how a `Chronicle` is actually assembled.

## 035 — Protagonist mortality

The brief: 15-20% of protagonists die before age 15, with a cause that varies by life stage (infant fever, childhood accident, childbirth, plague years, war with a neighboring village, feud violence from a long grudge, old age), and every death carries a short `causeOfDeath` plus prose.

- **`src/domain/mortality.ts`, new.** `protagonistMortalityBonus(ctx)` adds extra annual death probability on top of the existing village-wide actuarial curve (`actuarial.ts#deathProbabilityAtAge`, untouched) — age-banded (0, 1-4, 5-14) for the childhood target, plus context bonuses for a plague-flavored town event, a "conflict" town event at adult age (war), and an active feud (feud violence). `determineDeathCause(ctx)` picks ONE cause from the same context, most-specific first: childbirth (a mother who gave birth the previous simulated year) → plague → war → feud violence → infant fever (age 0) → childhood accident (age 1-14) → old age (70+) → illness (a same-year illness event) → misfortune (fallback).
- **Gated to the protagonist alone**, via `simulate.ts`'s existing `descriptor.personId === options.protagonistId` check in the "death" biology branch — the village-wide curve and every NPC's death are completely unaffected (see decision 037's determinism test).
- **Tuned empirically**, not from a closed-form formula — `deathProbabilityAtAge` is itself "deliberately crude approximations... good enough for a legends-mode toy simulator" (its own doc comment), and the bonus interacts with illness tripling, hardship-year multipliers and the safety-capped 100-year lifespan in ways not worth deriving by hand. `scripts/mortality-stats.ts` (new) runs N seeds through `generateWorld` + `simulate` with the rules engine and reports the age-at-death distribution, cause breakdown, decisions/life and chronicle entries/life. Constants were adjusted across several 60-150-seed runs (single small batches showed high variance — a ~60-seed batch swung between 8% and 25% at the SAME constants, consistent with the expected binomial noise at this probability and sample size) until a 150-seed run landed at 19.3% pre-15 mortality, inside the 15-20% target. See the final report for the full distribution.
- **Cause prose:** `narrate.ts`'s `death` case now reads `event.payload.cause` and, when present, renders "died of {cause phrase} at age N" / "was taken by {cause phrase}, at age N" instead of the old generic "died at age N" — an NPC death (no `cause` in its payload) is unaffected.

## 037 — Stop at death, and budget priority

- **`simulate()`'s year loop now breaks after a year in which `people[options.protagonistId].deathYear` becomes defined** — no-op with no `protagonistId` (the general village simulation always runs its full configured span; verified by a determinism-style test that checks the last snapshot year equals `config.endYear` and no death event carries a `cause` when `protagonistId` is omitted). A life world is generated with a 100-year safety-cap span (`startYear + 100`) rather than the town default's fixed 75, since "the sim writes their life until death" has to hold even for an unusually long-lived protagonist — `scripts/mortality-stats.ts`'s runs show this cap is essentially never reached in practice.
- **Budget priority (`LIFE_DECISION_BUDGET = 2000`, exported from `simulate.ts`):** once the running total of REAL `DecisionMaker.decide()` calls for a run reaches the budget, any further social decision NOT about the protagonist (`personId` and `partnerId` both `!== protagonistId`) is answered with the deterministic rule heuristic directly instead of calling the configured decision maker — the protagonist's own decisions, and decisions ABOUT them (like `AP1`), are never throttled. With the rules engine there's no real cost difference (it's the same pure function either way), so this is a structural guarantee for Jev rather than something visible in this worktree's own measurements; `scripts/mortality-stats.ts` shows actual decisions/life staying well under budget regardless (max 920 of 2000 across a 150-seed run).
- **`fork.ts#forkWorld` and `validate-override.ts#validateOverride` both gained the same optional `protagonistId` parameter**, threaded down to `simulate()`/`gatherCandidatesForYear` respectively — a rewrite of a protagonist life re-simulates with the SAME protagonist-only mechanics (extended catalog, mortality, stop-at-death) turned on, and validates against the SAME extended candidate set, or a protagonist-only decision id would validate against the wrong (NPC-only) candidate list and always fail.
- **Birth immutability, enforced in `validate-override.ts`:** with a `protagonistId` set, a rewrite targeting a year strictly before the protagonist's `birthYear` is rejected before candidate lookup even runs, with a message naming the birth year.

## 038 — The chronicle builder

`src/server/life-chronicle.ts` (new) maps a life's `SimulationResult` onto the contract's `Chronicle` — the protagonist-only counterpart to the existing town chronicle (`chronicle-data.ts#getChronicleData`), reusing every reusable piece rather than re-deriving prose from scratch.

- **Reused as-is:** `narratePersonTimeline("protagonist", ...)` for the base `{event, title, prose, significance}` list (its own `actors.includes(personId)` filter is exactly what makes every tick/entry protagonist-only — an event an NPC has entirely to themselves, like a career change with no shared actor, structurally never reaches the protagonist's timeline), `causeNounPhrase` for the `cause` annotation, `lifeSummary` for `summary`, `familyRelation` for `cast` relations, `renderPortrait` for a person sheet's `blurb`.
- **`{{personId}}` link marking is new** (`markLinks`): `narratePersonTimeline`'s prose already has real names substituted in; this post-processes it, replacing each actor's name with `{{id}}` and collecting `links`, rather than threading marker-aware templates through `narrate.ts`.
- **`Turn` construction (`buildTurn`/`deciderFor`/`whyPhraseFor`):** `decidedBy`/`deciderId` come from the underlying `DecisionRecord.personId` — `"self"` when it's the protagonist, `"chance"` for illness/death/immigration, `"lord"` for the levy, or the NPC's own id/name otherwise (this is what makes `AP1`, a rival's `A6` sabotage, or an NPC's `Y1` courtship of the protagonist show up correctly attributed). `whyPhrase` is derived from `fragility`/`surprise`/the chosen option's own probability, with the subject pronoun matching WHOEVER decided (self/NPC/"it" for chance) rather than always assuming the protagonist.
- **Level assignment (`levelFor`) reuses `isRealTurn` directly** (`chronicle-view.ts`, unchanged), with exactly one override: the protagonist's own death is ALWAYS level 3 with a turn, regardless of what `isRealTurn` would otherwise say — verified necessary in practice, since a very-old-age death (`deathProbabilityAtAge` ≥ 20%) can fail `isSurprise`'s default threshold and would otherwise fall through to level 2. Level 2 (ui-ux-handoff.md §7's "major event without an editable choice") is a small kind-based set (marriage, breakdown, town, levy, dream; a family death; a child's birth) plus a significance-score fallback (≥0.75); everything else is level 1.
- **Period summaries (`buildPeriodEntry`), the gap flagged twice before (decisions 032/033) and left unimplemented — built fresh this round.** Any run of 5+ consecutive years with zero protagonist chronicle entries becomes ONE `kind: "period"` entry (`level: 1`, with `endYear`), built from the protagonist's job/marital state at the snapshot for the gap's first year (not the branch's FINAL state, which could be much later in life) — "N quiet years passed in `<village>`; `<she/he>` working as `<a/an> <job>`, married to `{{spouseId}}`."
- **Scoping choice, disclosed:** a `DecisionRecord` that produced no event (e.g. `A1`'s "delay") never becomes a chronicle entry — there's no real moment to narrate, and `narratePersonTimeline` (and the pre-existing town chronicle) already work this way. `Turn.alternatives` still lists every option regardless, since building the turn doesn't require an event for the road not taken.

## 039 — Lives streaming design

- **`tick.entries` is built by replaying the FINISHED chronicle's entries, grouped by year, rather than narrating incrementally during the simulation loop.** True incremental narration would need significance scoring and cross-year causal lookups (period-gap detection in particular needs to see the WHOLE timeline) before the life is even finished — a materially bigger restructuring than this round's budget justified. The route runs `simulate()` to completion, registers the life/branch, calls `buildLifeChronicle`, then emits one `tick` per distinct year in chronicle order. This is a deliberate scoping choice, not an oversight: it satisfies the contract's frame shape (`start`, `tick` per year, `done`) and — since the rules engine has no real per-decision latency — the visible behavior for this worktree's testing is a fast burst of ticks followed by `done`; a real Jev run would show the same "SSE start, then everything at once" characteristic instead of the old world-stream endpoints' truly-incremental year-by-year feel. Flagged here for the UI side.
- **`lifeId`/`branchId` are minted BEFORE the simulation runs** (`newLifeId`/`newLifeBranchId`, `life-store.ts`), specifically so the `start` frame can carry the real ids the contract requires — `life-store.ts` gained `registerLife`/`registerLifeBranch` (taking a pre-minted id) alongside the original `createLife`/`addLifeBranch` (which mint their own, kept for scripts/tests that don't need this).
- **The `divergence` frame's `entryId`/`originalLabel`/`newLabel` come straight from the BASE branch's own `DecisionRecord`** (its `options` array, matched against `chosen` and the override's `optionId`) rather than rebuilding the base branch's chronicle just to look up one entry — `entryId` is `resultingEventIds[0]`, which is guaranteed to exist for any decision the UI could have shown a `Turn` for in the first place (a `Turn` is only ever built from a decision the chronicle-entry loop already found via `resultingEventIds`).
- **Ghosts, disclosed limitation:** built by comparing, for every new post-divergence entry with a `Turn`, whether the SAME `decisionId` exists in the base branch's decisions with a DIFFERENT `chosen` — correct when it fires, but many downstream decisions get a NEW, different `decisionId` after a fork (ids are content-derived and most embed the year, which the butterfly effect routinely shifts), so `ghosts` came back empty in both of this round's live rewrite tests even though the second one visibly changed later events (a new `Y5` friendship, `Y3` firing at a different year). The `divergence` frame itself still always carries the correct before/after for the turn actually being changed; a fuller diff-based ghost algorithm (walking the two branches' full entry lists by year, not just matching decision ids) is out of scope this round.

## 040 — The away catalog and narrative periods

A live Jev run (seed `smoke-1`, `Mara`/`f`) showed the protagonist's whole chronicle collapsing to 9 entries: after `1518 Leaves for a distant town`, the ONLY later entries were a single `1519 1519–1580` period (61 years, bare year range) and `1581 Dies`. Root cause: `gatherCandidatesForYear`'s entire social-decision catalog — courtship, career, children, friendship, faith, dreams, old age, all of it — is built from one loop over `aliveNonMoved`, which by construction excludes anyone (NPC or protagonist) with a `move` event carrying `away: true`. Once away, the protagonist kept facing `illness`/`death` (biology never excludes them) but literally nothing else — leaving town was a dead end, undermining the "what if she had left?" gameplay this game is built around.

- **A new away catalog, gathered in a separate block outside `aliveNonMoved`, protagonist-only, gated on `hasMovedAway`.** Reuses the SAME `DecisionKind`s as home life — Y1/A1 (courtship, marriage), A2 (children, asked via whichever of the couple is the mother), A3 (work, with an extra roll the year after arriving), Y5 (friendship), A7 (faith), A8 (dream check), A9 (temptation), A11 (breakdown), O1/O3/O4 (old age), PIL1 (pilgrimage) — zero new prompts, zero new rule-heuristics branches, zero new `DECISION_INSTRUCTIONS` entries to maintain, and nothing for decision 016's "no code-side weight on a Jev answer" to catch, since only trigger *timing* is new, never an answer distribution.
- **Other people met away are lightweight, deterministic newcomers (`Person.away: true`, ids `away-<year>`, `spawnAwayPerson` — same shape as `spawnImmigrant`)**, excluded from the home village's own illness/death/immigration-cap/courtship pools (`livingIds`, `aliveNonMoved`) so they never marry a home villager or die independently of the protagonist's own scenes. A newcomer joining the away cast is itself a code-rolled candidate (`away-arrival`, biology-style like immigration/levy — never a real DecisionMaker question) resolved in the SAME biology pass that runs before social `buildQuestion`, so a real `Person` already exists for that year's Y1/Y5 candidates to reference by id — no purity violation in the (read-only) `gatherCandidatesForYear`. A child born to an away couple inherits `away: true` too, or it would wrongly re-enter the home village's own pools.
- **The destination is named deterministically** (`pickAwayDestination`, keyed by seed + the leave year, reusing the `SURNAMES` pool + a settlement-kind word) instead of the old hardcoded `"a distant town"` — e.g. "Millbrook, a market town" on first mention, "Millbrook" on every later reference.
- **Home-village news reaches the away protagonist** by reusing C2 (a parent's death) with a relaxed trigger (any age, while away, not just "still a minor") and an `extra.awayNews`/`relative` flag that reframes the SAME grieve-openly/harden/lean-on-family prose as "Word came from `<home town>` that her father had died. ..." (`narrate.ts`'s `reflection` case).
- **Returning home is a small yearly code-rolled chance (`"return"`, biology-style, not a DecisionMaker question)** once 3+ years away — resolving to it pushes a fresh `move` event with `away: false`, which is all `hasMovedAway` needs to treat them as home again from the next year on, rejoining `aliveNonMoved` and the ordinary home catalog. A protagonist can leave, return, and leave again; each cycle is independently deterministic.
- **Period titles are now narrative** (`periodTitle` in `life-chronicle.ts`: life-stage- or trade-based, e.g. "Early childhood in Ashford", "Years at the forge in Millbrook"), NEVER the bare `"1519–1580"` the bug report flagged, plus one extra deterministic sentence built from whichever low-significance event kinds actually happened during the gap (`periodDetailSentence` — illness, a trade shift, a quarrel, etc.), on top of the existing job/spouse sentence. The place name in a period now tracks whether the protagonist was away at that point (`placeNameAt`), not always the home town.
- **Trigger-rate tuning only, per decision 016's ban on weighting Jev's answers:** `richness-stats.ts` (new, `mortality-stats.ts`'s style) showed full-length (50+ year) lives that LEAVE landing solidly in the 25-35 chronicle-entry range — the direct fix for the reported bug — while full-length lives that STAY were thinner (16-24). Widened the protagonist-only Y5 friendship window (age 14-30 → 14-50, gate 0.06 → 0.1) and nudged A7/A9/O1/O3's gates up (0.12/0.05/0.1/0.1 → 0.18/0.08/0.15/0.15) — all four already protagonist-only dials introduced by decision 036, never shared with NPCs, so this cannot touch town-wide behavior or any existing test's NPC counts. O2/O4 were deliberately left alone: they're shared with the original 14-kind NPC catalog.
- **Disclosed, not fixed this round:** a stayed full-length life still averages ~15-20 entries against the 30-60 target (below it, though nowhere near the original 9-entry bug), and an occasional long period (up to ~28 years in a 20-seed sweep) still occurs for a stayed protagonist who never marries or takes up faith — those whole situation categories (A2, A9, A7, PIL1) simply never gate open for them. A deeper fix would mean loosening the marriage-independent triggers (C3, Y2, A8, A3, O1/O3/O4) further or adding new marriage-independent situations — left as a follow-up rather than risking a broader, less-validated retune under this round's budget. Also disclosed: away-catalog prose (courtship, work, etc.) doesn't explicitly re-mention the destination's name per event the way the "moved away to X" and period-title lines do — a reader has to remember they're away from context, not from every sentence.
- **Verified:** `src/domain/protagonist.test.ts` (the away protagonist gets real, non-illness/death candidates while away; a full simulated life that leaves keeps producing real events well after departure, tried across up to 20 seeds since leaving is a probabilistic roll), `src/server/life-chronicle.test.ts` (a period title is never a bare year range, both on a synthetic fixture and across 8 real simulated lives), `pnpm typecheck`/`pnpm test`/`pnpm lint` all clean. `scripts/richness-stats.ts` over 20 seeds: 0 bare period titles; full-length left lives ~25-35 entries; full-length stayed lives ~16-24 (see disclosed gap above). One live Jev run (seed `decision-040-1`, `Rowan`/`m`, stayed in Ashford for 76 years): 18 chronicle entries, 7 real turns, 522 `jevCalls` (515 cache hits — 7 real calls), 33.7s wall time.

## 041 — Let fate decide: a name-informed SEX1

The brief: `sex: "random"` used to roll a keyed coin blind to the name (`worldgen.ts`'s old `sexRng() < 0.5`). A clearly gendered name (`Lucía`, `Tomás`) should read as such almost always; an ambiguous one should be a real toss-up.

- **`resolveProtagonistSex` (`src/domain/worldgen.ts`, new), called from `src/app/api/lives/stream/route.ts` BEFORE `generateWorld`** — there is no protagonist and no `PersonMind` yet, so the question is deliberately minimal: `{ name, setting: "a medieval European village, around 1500" }`, not a full `self.mind`/`self.portrait` state like every other `DecisionKind`. A new `DecisionKind` (`SEX1`, `decisions.ts`), options `["f", "m"]`, question id `sex1:<lowercased name>` (content-derived, so it's cached across runs/seeds for the same name — Jev's judgment on "Lucía" doesn't need re-asking every time someone names their protagonist that).
- **Sampled with the same keyed Gumbel-max helper every other decision uses** (`sampleGumbelMax`, `rng.ts`), keyed by `(seed, "protagonist", startYear, "SEX1")` — per the brief's exact spec. This key does NOT include the name (only the DISTRIBUTION Jev returns does), which has a subtle consequence verified live (see below): two different names on the SAME seed draw from the SAME Gumbel noise per option, so a name Jev is only moderately confident about can still land on the minority sex — a real coin flip, not a rigged one.
- **`worldgen.ts`'s own `protagonist.sex === "random"` fallback (the old blind coin flip) is UNCHANGED** — `resolveProtagonistSex` only intercepts the `/api/lives/stream` route; `scripts/mortality-stats.ts`, `scripts/richness-stats.ts` and the rules-engine tests still pass `sex: "random"` straight through to `generateWorld`, which is fine for them (no name-reading DecisionMaker call needed for a rules-engine or synthetic-name run) and keeps every existing test byte-identical.
- **Never a `DecisionRecord`, never a chronicle turn** — the birth stays immutable and un-forkable, exactly as before this change. `DECISION_INSTRUCTIONS`/criteria (`jev-decision-maker.ts`) and `ruleDistribution`'s `SEX1` case (`rule-heuristics.ts`, a flat 50/50 — the rules engine has no opinion on a name's gendering) are both required for `pnpm typecheck` to pass against the widened `DecisionKind` union, same as every prior round's additions.
- **Verified:** `src/domain/worldgen.test.ts` (new) with a fake `DecisionMaker` — an f-heavy distribution resolves to `f` in 20/20 seeds, an m-heavy one to `m` in 20/20, and the same seed+name pair is deterministic across repeated calls. `pnpm typecheck`/`pnpm test`/`pnpm lint` all clean. Two live Jev runs, same seed (`d1-live-1`): `Lucía` → Jev's own `{f: 0.67, m: 0.33}` (cached raw distribution, `.cache/jev-decisions.json`), resolved to `m` — the minority branch, landed on because this seed's fixed per-option Gumbel noise happened to favor `m` strongly enough to overcome the log-probability gap; `Tomás` → also resolved to `m` (consistent with a heavily male-leaning name). Disclosed: with a 67/33 split, "almost always gets the expected sex" is closer to "usually" for a name Jev isn't fully confident about — this is Jev's own calibration, correctly left unweighted per decision 016, not a code-side bug.

## 042 — A yearly beat for the protagonist

The brief: at least one chronicle entry for every year of the protagonist's life, birth to death — a 76-year life had ~18 entries before this round. This deliberately overrides decision 038's "summarize quiet years" rule for the protagonist specifically (period summaries stay dead code for anyone else who might use them later, per the brief — nothing else in this codebase does, so they were removed rather than left to bit-rot unverified).

- **One generic `DecisionKind` (`D1`, "daily life"), never dozens** — everything vignette-specific (eligibility by age/place/job/household/season/town-event, the first-person question, each outcome's prose and mind effect) lives in a new pure module, `src/domain/vignettes.ts`, parameterized by a `vignette` id carried in `situation.vignette`. `jev-decision-maker.ts`'s `D1` instruction is fully generic ("read situation.vignette/situation.question for the everyday moment you're facing…"); `rule-heuristics.ts`'s `D1` case is a uniform-ish spread over whichever 2-3 options the vignette offers (a small lean toward `options[0]` via `self.altruism`, matching the mild self-consistency other rule branches show, never a fake per-vignette model).
- **12 vignettes** covering the brief's examples (a hard winter, a good/poor harvest, market day, learning a skill from a parent, a sibling quarrel, a neighbor needing help, a first glance, a feast day, a sick animal, an old debt, teaching a child, the aches of age) — `hard-winter`/`poor-harvest`/`good-harvest` gate on `town.ts#seasonFor` (a REAL eligibility input here, not just atmospheric color like everywhere else it's used) crossed with the year's town event; `feast-day` is eligible in every context, guaranteeing `pickVignette` (keyed RNG over the eligible subset) never comes up empty regardless of age, place, household or season.
- **Injected in `simulate.ts`'s yearly loop, AFTER biology and social resolution for the year, not at candidate-gathering time** — checked by ACTUAL OUTCOME (`events.some(e => e.year === year && e.actors.includes(protagonistId))`), not by candidate presence, because a real situation can still resolve to "nothing happens" (Y1's `wait`, A1's `delay` — no event, by decision 038's existing scoping choice) and would otherwise leave a silent year despite a candidate having been offered. A `D1` outcome always produces a `vignette` event regardless of which option wins (unlike the asymmetric kinds above), which is what makes the per-year guarantee structural rather than probabilistic. Never budget-throttled (`LIFE_DECISION_BUDGET`) — it's always about the protagonist, same exemption as their other decisions (decision 037). Still overridable (`D1:<protagonistId>:<year>`), so a rewrite can change what an otherwise-quiet year held.
- **New `EventKind` (`"vignette"`, `types.ts`)** rather than folding into `"reflection"` — a clean render path (`narrate.ts`'s new `"vignette"` case in both `narrateEvent` and `titleFor`, looked up from `vignettes.ts` by `payload.vignette` + `payload.outcome`) with its own narrative title (`vignette.title(townName)`, e.g. "A hard winter", "Market day in Millbrook") independent of `"reflection"`'s existing `note`-keyed machinery and its away-news framing branch, which don't apply here. `titleFor` gained a `townName` parameter (threaded from `narrateEventForViewer`) it didn't need before this.
- **Level 1 by default, level 3 only via `isRealTurn`, per the brief** — `life-chronicle.ts#levelFor` special-cases `event.kind === "vignette"` to skip the generic `significance >= 0.75` → level 2 bump every other kind gets, so an ordinary year never masquerades as "a major event without an editable choice" just because Jev scored it highly.
- **`life-chronicle.ts`'s period-summary machinery removed** (`buildPeriodEntry`, `periodTitle`, `periodDetailSentence`, `placeNameAt`, `JOB_PLACE_NOUN`, `PERIOD_GAP_THRESHOLD_YEARS`) — this file is the protagonist-only chronicle builder (decision 038's own docstring), and with every year now covered, `gapEnd - gapStart + 1 >= PERIOD_GAP_THRESHOLD_YEARS` can structurally never trigger. The town-facing `chronicle-data.ts` has its own independent code path and is untouched. `"period"` stays in the `ChronicleEntry.kind` contract type (harmless, and still used by `src/lib/fixtures/data.ts`'s UI mock data) — only the server-side generator was removed.
- **Disclosed, not fixed this round:** the vignette pool skews adult (8 of 12 need `age >= 14`, a spouse-implying context, or a job a child doesn't have yet) — a live run of a child who dies young (see decision 041's verification) shows `"Learning the trade"` repeating 4 times in an 11-entry, 10-year life; a deeper fix would add more childhood-specific vignettes. Also disclosed: `validate-override.ts` reconstructs a year's candidates from `gatherCandidatesForYear` alone, which has no knowledge of `D1` (it's injected only after outcome resolution, not at candidate-gathering time) — a rewrite targeting a `D1:<protagonistId>:<year>` decision id is not yet supported by the fork/override path; out of scope for this round's verification (which doesn't exercise `/rewrite`).
- **Verified:** `src/server/life-chronicle.test.ts` (no year of the protagonist's life is missing an entry, across 8 real simulated lives; no `"period"` entry is ever produced). `pnpm typecheck`/`pnpm test`/`pnpm lint` all clean. `scripts/richness-stats.ts` over 20 seeds (rules engine): minimum entries/year across ALL seeds is 1, total missing protagonist-years is 0; entries/life rose from the old ~18-entry 76-year baseline to 39-83 across the sweep (avg 42.5 stayed / 69.3 left). Two live Jev runs (seed `d1-live-1`): `Lucía` (resolved `m`, died at 9) — 11 entries, all 10 years covered, 102 `jevCalls` (861 cache hits), 7.7s wall time; `Tomás` (also resolved `m`, same seed) — 11 entries, all 10 years covered, 102 `jevCalls` (954 cache hits), 2.8s wall time. The two runs' event sequences came out identical past the `SEX1` call: expected, not a bug — every other decision's Gumbel key is `(seed, "protagonist", year, kind)`, not name-dependent, so once both names resolved to the same sex on the same seed, identical mind facets (seeded by `(seed, "protagonist", startYear)`, also name-independent) and identical noise draws produced the same outcomes throughout.

## 043 — D1 forking, and a child-appropriate vignette pool

The brief: close decision 042's two disclosed gaps — `D1` decisions couldn't be forked, and the vignette pool skewed adult, with child lives repeating "Learning the trade."

- **`D1` now forks like any other decision.** The pure candidate-building step of `resolveDailyLifeVignette` (ctx assembly, `pickVignette`, the `CandidateDescriptor`) is extracted into `buildDailyLifeVignetteDescriptor`, a shared pure function. `gatherCandidatesForYear` now calls it too, pushing a `D1:<protagonistId>:<year>` candidate for the protagonist every year (unconditionally — `feast-day`'s near-universal eligibility means this is never a false negative), so `validate-override.ts`'s existing `gatherCandidatesForYear`-based reconstruction finds it, exactly like every other decision. Since `D1` is also in `SOCIAL_KINDS` (pre-existing), it's explicitly excluded from `simulate()`'s generic per-kind `socialCandidates` loop — it keeps its own dedicated call site (`resolveDailyLifeVignette`, gated on "no event yet this year"), so it's never double-resolved. Validation and simulation can never disagree about what a `D1` decision at a given protagonist-year looks like, because both now call the same function.
- **Age-appropriate vignettes, three bands, 15 new entries in `vignettes.ts`** (27 total): early childhood 0-5 (a fever scare, a first wobbling step, a new sibling, lost in the woods, a village festival through young eyes), childhood 6-12 (helping in the fields, a friend's secret, a scolding from the priest, a stray dog, a fight with another child, carrying water in winter), youth 13-19 (a first dance at the feast, a dare, work alongside a master, an argument with a parent over the future).

The protagonist still lives the outcome (thought, memory, relationship nudge land on their own mind) — only who gets credit for the choice changes. `learning-a-skill` and the three seasonal self-decided vignettes (`hard-winter`, `poor-harvest`/`good-harvest`, `feast-day`) gained an `age >= 3` (`learning-a-skill`: `age >= 6`) floor, since they're all first-person ("Do I...?") and weren't previously age-gated at the bottom — a 1-year-old was being asked "Do I pay close attention?" before this round.
- **No repeat within 5 years, deterministic.** `pickVignette` takes an optional `recentIds` set; `buildDailyLifeVignetteDescriptor` computes it from the actual event log (`kind === "vignette"` events for this protagonist in `[year-5, year-1]`) and excludes those ids from the eligible pool — falling back to the full eligible set (never a re-roll) if every eligible vignette was used recently, so a year is never left without one.
- **Verified:** `src/domain/protagonist.test.ts` gained a fork test — a real `D1` decision from a simulated protagonist life is forced to its other option; `validateOverride` accepts it (this was the exact bug), every event before the fork year is unchanged, and the forked branch's `D1` decision's `chosen` differs from the original. `pnpm typecheck`/`pnpm test` (127 passing)/`pnpm lint` all clean. `scripts/richness-stats.ts` (extended to report `maxVignetteRepeat` per life) over 20 seeds: young-child lives (ages 1-11 at death) now show a max single-vignette repeat of 0-1, down from decision 042's disclosed baseline of 4 repeats in an 11-entry, 10-year life; older lives that live for decades can still repeat a given vignette more than once (each repeat still at least 5 years apart, per the literal "within 5 years" rule — worst observed was 11 repeats across a 60-year, 63-entry life). One live run (rules engine, seed `d1-kids-1`): the first 12 chronicle entries include three parent-decided early-childhood vignettes ("A fever scare" and "A first, wobbling step" at ages 1 and 5, both `decidedBy: "Greta Duskwood's choice"`) plus a "A village festival, through young eyes" at age 2 — no repeated "Learning the trade".

## 044 — Jev selects what happens: one batched request per person-year

The brief: Jev, not code and RNG, should decide WHAT happens to people each year (not just how they respond), and should be used to the max — this project is a Jev test bed. Every prior round asked Jev exactly one question per request, re-paying the whole mind/portrait state every time (docs/findings.md "Jev throughput limits": the state is paid once per request, and the sustained limit is 1,200 requests/min).

- **`DecisionMaker` gains `decideYear(batch)`** (`src/domain/decisions.ts`): one request per person per year. `PersonYearBatch` carries the person's `self` (mind/portrait + year context), paid once, plus a `situations` map of every candidate `gatherCandidatesForYear` already decided was ELIGIBLE this year. `PersonYearResult` returns, per situation: an `occurrence` Noul ("how likely is `situations.<id>` to happen this year, in a TYPICAL year" — occurrence-calibration framing per the brief's point 7, not a code-side weight, per decision 016), and a speculative `response` Choice, asked for every candidate whether or not it occurs (speculative fan-out, docs.typesafe.ai/patterns/fan-out.md — "additional questions usually have little effect on response time"). `RuleDecisionMaker` implements it too (a pure, deterministic occurrence heuristic — 0.85 once eligible, 0.3 for `D1`), so tests stay offline.
- **`simulate.ts` batches per person, not per candidate.** All of a person's `socialCandidates` for the year, PLUS their `D1` daily-life candidate (now riding in the SAME batch instead of a separate call — see below), are grouped by `personId` and answered with one `decideYear` call; requests for different people within a year run in parallel (`yearBatchConcurrency`, default 64). An adapter that doesn't implement `decideYear` (a minimal test double) still gets the old one-`decide()`-per-candidate path — the port change is additive and backward compatible.
- **`JevDecisionMaker`** adds a token-bucket rate limiter (`src/adapters/decision/rate-limiter.ts`, default 18 req/s sustained, burst 100 — conservative against the documented 1,200/min), a widened SDK `RetryPolicy` (the SDK already retries 429/500-599 including 529 with exponential backoff + jitter — decision 044 just raises `maxRetries` from the SDK's default of 2 to 6, since a batched person-year request is costlier to lose), and splits a batch across multiple requests if its estimated size (`estimateTokens`, ~4 chars/token) would exceed `JEV_YEAR_TOKEN_BUDGET` (55k, under the documented 64k hard cap). Cached per request, keyed by state + questions + model (`decisionCacheKey`, the same fix as commit `e2c1d82`) — a fork re-simulating an unchanged person-year hits the cache instead of re-asking Jev.
- **`DecisionRecord`/`Turn` gain an optional `occurrenceProbability`** — Jev's own occurrence judgment, stored alongside `jevRaw`/`final` (never blended into them, per decision 016), so "Why this happened" can eventually say "this was likely to happen this year" vs "this was unlikely to happen at all". Backward compatible (optional, additive only).

**Disclosed, not fixed this round — the scope cuts, and why:**

- **Code still decides ELIGIBILITY *and* keeps its existing probabilistic trigger gates** (the `keyedDraw` rolls in `gatherCandidatesForYear` — e.g. `seekChance` for Y1, `moveChance` for Y3, `feudDraw` for Y4). The brief asked for eligibility to be PURE (age/marital-status/place/relationship/cooldown conditions only), with Jev's new `occurrence` Noul replacing every random gating roll. That would mean rewriting roughly twenty trigger sites across a heavily-tuned, already-measured demographic and narrative system (population growth, marriage rates, chronicle density — decisions 012, 016, 028, 040) with no budget left this round to re-measure the fallout the way decisions 040/043 did with `richness-stats.ts`/`mortality-stats.ts`. Given how carefully those numbers were earned, retuning them blind was judged a worse risk than leaving this round's `occurrence` question as REPORTED (real, asked, stored, cached) but not YET load-bearing for whether a Y1/A2/A3/etc. candidate fires.
